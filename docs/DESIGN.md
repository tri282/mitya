# Mitya — Architecture Overview

Goal: A local LLM that writes like Fyodor Dostoevsky and answers grounded in his 5 novels, on a single 6GB GPU.  
*Requirements: Mistral-7B QLoRA fine-tune (done); metadata-tagged RAG over the novels (built and evaluated, `docs/RAG.md` §VI–§VII); GPU budget ≤ 6GB; all retrieval on CPU.*  

Mitya splits into two independent subsystems: **Style** (a Dostoevsky-voiced fine-tune) and **Substance** (RAG grounding over the actual texts), plus a thin third piece, **UI** (a browser client over the existing FastAPI `/chat` SSE endpoint — built). The two backend subsystems compose at generation time — RAG supplies passages, the fine-tuned model answers in character, and citations are shown programmatically rather than asked of the model. Every design choice in all three is bounded by a single 6GB consumer GPU (the UI adds no GPU consumer of its own).

## I. System Overview

```txt
OFFLINE                                    ONLINE
--------                                    ------
PDFs -> OCR -> chunk -> synthetic Q&A       llama-server (Mitya GGUF, GPU)
  -> QLoRA fine-tune -> merge -> GGUF              ^
  (src/ingestion.py, src/training.py,              | persona + context prompt
   scripts/build_dataset.py, quantize.sh)          |
                                             src/api/app.py (FastAPI, SSE)
Dostoevsky .txt corpus -> per-book parse           ^                  ^
  -> chunk -> embed -> Qdrant upsert                | query           | fetch + SSE (ReadableStream)
  -> entities.json / summaries.json           router -> retrieve -> rerank
  (src/rag/ingest.py, scripts/build_*.py)      (src/rag/*, CPU only)  |
                                                          browser: Vue 3 SPA (frontend/)
                                                          served by StaticFiles (prod) /
                                                          Vite dev-proxy (dev) — see §VI
```

Offline work produces two static artifacts: the quantized GGUF model and the Qdrant collection + entity/summary JSON. Online, a query is routed, retrieved and reranked entirely on CPU, then handed to `llama-server` — the only GPU consumer — for in-character generation. The browser client is a thin, stateless-on-the-server SPA: it talks only to `src/api/app.py`'s existing `/chat`/`/health`/`/books` routes and adds no new backend component.

## II. Part 1 — Style (fine-tune)

> **HISTORICAL as of v2 CP2 (2026-08-28), per charter D2.** The fine-tune is **out of the
> request path**: `/chat` is served by a hosted provider through the gateway, and `local-q4km`
> is a frozen chart line rather than a live arm (A3). This section documents how the artifact
> was produced and stays accurate about that; it no longer describes what answers a user.
>
> One consequence is live, not historical. With the fine-tune out of the path the persona
> prompt stopped being "the fine-tune's identity" and became an ordinary prompt — so
> `PERSONA_HEAD` moved onto the versioned serving config and is now a P7 search axis (R61).
> `src/training.py`'s `SYSTEM_PROMPT` is deliberately **not** wired to it: that constant records
> what the model was *trained* on, which is history and must not drift when a serving knob is
> tuned. The two were byte-identical at 208 characters when they were split; from here they are
> free to diverge, and that divergence is the point.

* Base model `unsloth/mistral-7b-instruct-v0.3-bnb-4bit`, fine-tuned with **QLoRA** via **Unsloth** (`SFTTrainer`/`trl`).
* Training data: synthetic Q&A generated by a teacher LLM (Gemini/Ollama) from OCR'd novel chunks — a question-generation pass, then an answer pass in Dostoevsky's first-person voice, formatted as **ChatML** (system/user/assistant).
* Merge LoRA adapters into the base (`merge_and_unload()`), quantize via `llama.cpp` to `q4_k_m` / `q5_k_m` (also `q8_0`).

*See `docs/FINE_TUNE.md` for the full pipeline.*

## III. Part 2 — Substance (RAG)

High-level pipeline (**built and serving** since v2; the generation leg moved to the gateway at CP2):

* Clean-plaintext corpus (`data/rag/*.txt`, no OCR) — one novel per file.
* Per-book structural parser emits chunks plus a `structure.json` manifest (book/part/chapter tree), since heading formats differ per book.
* Ingest to **Qdrant** (local mode): hybrid dense (`nomic-embed-text-v1.5` via fastembed) + sparse (BM25 via fastembed, IDF-weighted), fused server-side with Qdrant's **native RRF**.
* **FlashRank** reranks the fused top-25 down to top-3.
* An **entity map** (`entities.json`, teacher-LLM + human review) resolves query terms to canonical names/aliases and expands the query text before embedding.
* A deterministic **DEFAULT | STRUCTURAL** router: STRUCTURAL only when a summary-intent keyword *and* a resolvable chapter scope both hold (backed by pre-generated `summaries.json`); everything else is DEFAULT hybrid retrieval.
* Generation is **single-pass**: the persona answers in character from the retrieved passages, with a **programmatic Sources list** appended after the stream — no inline citations. **Since v2 CP2 this bullet points at the gateway, not the fine-tune** (charter D5: the RAG substance persists, its generation leg moved). `src/rag/generate.py` selects a provider from the versioned `Config.SERVING_MODEL`, enforces spend before the call, and returns the same token stream its callers always read; `src/api/app.py` stays provider-neutral. Retrieval, fusion, reranking and the entity map above are **unchanged** — they run before the model is chosen and are identical on every arm, which is why no retrieval-derived signal can discriminate between arms (R59).

*See `docs/RAG.md` for the settled design and its rationale, and `plans/mitya-v2/research/p2-findings.md` for what CP2 measured.*

## IV. How the two compose

RAG retrieves passages; the fine-tuned model never saw retrieved context during training and its persona explicitly refuses references to external sources. Rather than fight that conditioning with citation instructions, the system prompt keeps the fine-tuned persona text verbatim and frames the passages as the author's **own recollections** — first-person-compatible, and aligned with (not against) the "no external references" training. Grounding is shown to the user as a **programmatic Sources list**, built from retrieval metadata after generation completes, independent of whether the model cooperates. See `docs/RAG.md` §III.4 for the exact prompt composition.

## V. Hardware Budget

> **HISTORICAL as of v2 CP2 (2026-08-28) — superseded by hosted serving, not deleted.** Nothing
> in the request path starts `llama-server`; the GPU budget below governs only the offline
> evaluation path (`src/gateway/local.py`) and the frozen baseline that cites these numbers.
> `docs/RAG.md` §V carries the same arithmetic and the two copies must stay consistent.
>
> What replaced it is a **cost** budget rather than a VRAM one: measured USD/answer at CP2 is
> $0.000500 (Groq `gpt-oss-120b`) and $0.001473 (`gemini-3.5-flash-lite`), both list-rate
> estimates at the free tier and never spend (R48, R67).

The 6GB GPU runs **only** the quantized LLM (`q4_k_m`, ≈5.2–5.5GB total with KV cache and compute buffers); every retrieval component (embedding, BM25, Qdrant, reranking) runs on CPU, and within a request the two phases are sequential, so there is no GPU contention. See `docs/RAG.md` §V for the full arithmetic and the `llama-server` launch flags.

## VI. Part 3 — UI

A thin browser client over the existing `/chat` SSE endpoint — no new backend surface beyond the two shipped contract deltas (below).
* **Stack:** Vue 3 (`<script setup>`) + Vite + TypeScript.
* **API boundary:** all network access typed and confined to `frontend/src/api/*`; `/chat`'s SSE response is read via `fetch` + `response.body.getReader()` (the browser's `EventSource` cannot `POST`), never `EventSource`.
* **Serving:** production build (`frontend/dist/`) is mounted last by FastAPI via `StaticFiles(html=True)`, after all API routes; dev runs Vite's own server with a proxy to `127.0.0.1:8000` for `/chat`, `/health`, `/books`. Same relative paths in both modes — no hardcoded host, no CORS.
* **Visual system:** the single dim "Evening Reading Room" theme (see root `DESIGN.md`) — warm near-black surface, one amber "lamplight" accent, literary serif reading column, quiet sans chrome. No light theme in v1.
* **Backend contract deltas (shipped):** (1) an `event: meta` SSE event carrying per-answer diagnostics (`route_name, chunk_ids, ttft_ms, total_ms, filter_relaxed, no_context, cache_hit`, and from v2 CP1 also `request_id, tenant, cost_usd, cost_metered, config_version, corpus_version`) for a collapsed debug panel; (2) the `cache.py` cached value changed from a bare answer string to `{answer, sources, footer}` so a cache hit re-emits the `sources` event and grounding stays visible on repeat questions. Both are additive, local-only (no new request flag) — see `docs/RAG.md` §III.6/§IV.1 for the full contract. `frontend/` (the Vue 3 SPA) is built and served in production via a mount-last `StaticFiles`; see the repo README for build/run notes.

* **Auth-gated state (v2 CP5):** the SPA is behind a **login wall**. An unauthenticated visitor sees
  the login view and nothing else — no corpus browsing, no public demo tenant. Session state lives in
  `frontend/src/state/auth.ts`; `LoginView.vue` is the only surface reachable without a session.
  Deliberately minimal: D8 rules out ceremony, and auth is not a new product surface here.
* **Session expiry is two cases, and only one can be a 401.** Expiry *before* `/chat` answers is a
  clean `401` and the SPA returns to the login view. Expiry *after* the first token cannot be a 401
  at all — the `200` is already committed and the stream is in flight — so the in-flight answer
  completes and the **next** request is refused. Measured end-to-end at CP5: 15 frames delivered
  after the session was destroyed mid-stream, then `401` on the following call.

*See `DESIGN.md` (repo root) for the visual system and `docs/RAG.md` §IV.1 for the SSE contract.*

> **Amended 2026-08-29 (charter A13, `plans/mitya-v2/02-decide/decisions.md` Q3).** CP7's
> objective is **cost**, not quality: search over retrieval/prompt/allocation config for the
> cheapest configuration whose quality is **non-inferior at the measured MDE**, proposals gated
> through the CP3 eval gate (`docs/RAG.md` §VII.4) like any human change. The original
> quality-search question is closed as a measured negative (R20, R72, R63) — no quality
> improvement this system can produce is detectable at any n this project will reach — and is
> published as a first-class finding, not subsumed under the cost headline.
>
> **A13's rider is deliberate and still open:** A13 fixes the objective (cost) and the guard's
> *form* (non-inferiority at the measured MDE). It does **not** fix the guard's *composition* —
> which quality dimensions it contains, or how groundedness trades against persona retention.
> That weighting is a decision for when the full picture exists, not one to hard-code from
> today's evidence. Any component needing a single scalar "best" before then must state its
> weighting inline and mark it provisional. Do not read a fixed quality-scoring formula into this
> section; none is settled.
